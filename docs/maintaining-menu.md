# Maintaining categories and dishes

This is the everyday editing guide. The menu is stored in local files; there is no admin website or database to log into. A “dish” below means any drink, food item, or topping.

Related guides: [Discovery banner](discovery-guide.md) · [Photo tools](image-workflow.md).

## Start here

1. Make a backup of the project before a batch of edits. At minimum keep `src/`, `scripts/`, `public/`, `package.json`, and `package-lock.json` together. A backup of only the menu JSON cannot restore deleted photos.
2. Open Terminal in the website folder:

   ```sh
   cd '/Users/james.tran/Desktop/agents/gpt/cazone/website'
   npm run dev
   ```

3. Open `http://localhost:4321/`. Save changes in your editor, then review the preview. Astro normally refreshes it automatically.
4. Finish each batch with:

   ```sh
   npm run menu:check
   npm run build
   ```

`menu:check` validates the current catalog, photo paths/mapping references and Discovery references without expecting a fixed number of items or fixed prices. `build` also checks TypeScript and generates the static website. Neither command publishes anything.

Use `npm install` once when setting up a new copy of the project; Node.js 22.12 or later is required. Changes made on localhost will not update a future public website until it is rebuilt and deployed.

## Files you edit

| Purpose | File |
| --- | --- |
| Category and dish content | `src/data/products.json` |
| Discovery banner | `src/data/menu.ts`, inside `discovery` |
| Which source photos belong to which dishes | `scripts/product-photos.json` |
| Photo files/URLs for the website | Generated by the image script; do not hand-edit `src/data/photo-assets.json` |

`products.json` contains two arrays: `categories` and `products`. Keep its `schemaVersion`, `currency`, and `contentStatus` metadata as they are. Content counts shown on the website are calculated automatically.

JSON needs double quotes, commas **between** entries, and no trailing comma after the final entry. It does not allow comments. The examples below are entries to insert into the relevant array, not replacements for the whole file. Example names and prices are illustrative; enter your actual approved content.

IDs such as `coffee` and `bac-xiu` connect records together. Use unique lowercase IDs with hyphens and no accents or spaces. Keep an ID when merely renaming an item; changing its ID requires updating every reference.

## Add a category

Insert a category object into `categories`, in the position where it should appear in navigation and on the page:

```json
{
  "id": "seasonal",
  "name": { "vi": "Theo mùa", "en": "Seasonal" },
  "subtitle": { "vi": "Một chút hương vị theo mùa.", "en": "A little taste of the season." }
}
```

Then add at least one product whose `categoryId` is `seasonal` (example below). An empty category currently still displays a heading; it is not automatically hidden.

Two presentation rules currently live in code:

- **New drink category:** add `'seasonal'` to `drinkCategories` in `src/domain/presentation.ts`. This makes its drinks sort by their displayed first-variant price, highest first. Example: `new Set(['signature', 'coffee', 'tea', 'milk-tea', 'matcha', 'healthy', 'seasonal'])`.
- **New food category:** leave it out of `drinkCategories` to preserve manual order. To give it the food icon for missing photos, add its ID to `['food', 'sweet']` in the `placeholder` selection in `src/data/menu.ts`, for example `['food', 'sweet', 'bakery']`. Other new categories default to the drink icon. The existing `toppings` ID receives the topping icon.

The dark/yellow Signature treatment is tied to category ID `signature`. Rename its visible VI/EN text freely, but retain this ID to keep that treatment.

## Update or reorder a category

- Change `name.vi`, `name.en`, `subtitle.vi`, and `subtitle.en` to edit the text.
- Move the entire category object up or down in `categories` to change its order. Section numbers and navigation follow automatically.
- Move a dish between categories by changing the dish's `categoryId` to an existing category ID.
- Editing a category name does not require changing any dish or photo ID.

## Remove a category

1. Move its dishes to another category, or remove those dishes using the dish-removal steps below.
2. If it is `discovery.targetCategory`, change that target to a category you are keeping. References must remain valid even when Discovery is disabled.
3. Remove the category object from `categories`.
4. If its ID is in `drinkCategories` or the food placeholder list described above, remove it there too.
5. Run `npm run menu:check` and `npm run build`.

Do not leave dishes pointing to a deleted category. That is a validation error.

## Add a dish

Add this shape to `products`, using your own names, prices and a category that exists:

```json
{
  "id": "seasonal-latte",
  "categoryId": "seasonal",
  "name": { "vi": "Latte theo mùa", "en": "Seasonal latte" },
  "summary": { "vi": "Cà phê và sữa tươi.", "en": "Coffee with fresh milk." },
  "description": { "vi": "Cà phê kết hợp sữa tươi, phục vụ lạnh.", "en": "Coffee with fresh milk, served iced." },
  "badges": [],
  "availability": "available",
  "aliases": [],
  "sourceCodes": [],
  "optionGroups": [],
  "variants": [
    {
      "id": "s-cold",
      "label": { "vi": "S · Đá", "en": "S · Iced" },
      "price": 55000,
      "availability": "available",
      "attributes": { "size": "S", "temperature": "cold" },
      "benefits": []
    },
    {
      "id": "m-cold",
      "label": { "vi": "M · Đá", "en": "M · Iced" },
      "price": 65000,
      "availability": "available",
      "attributes": { "size": "M", "temperature": "cold" },
      "benefits": []
    }
  ]
}
```

No photo is required to add a dish. Without a photo mapping, the website uses a category icon. Follow [the photo guide](image-workflow.md#add-or-replace-one-dishs-photos) when you have one.

For a food item with a single price, use one variant with `id: "portion"`, a label such as `{ "vi": "Một phần", "en": "One portion" }`, and `attributes: {}`. Every dish must retain at least one variant.

Some older source records contain `image` and `imageAlt` fields pointing to illustrations. **These are overridden by the photo adapter.** Do not edit those fields to change a photo, and do not copy them into new dishes. Use the photo mapping instead.

## Update a dish

| Change | What to edit |
| --- | --- |
| Display name | Both languages of `name`; keep `id` unchanged |
| Short catalog description | `summary.vi` / `summary.en` |
| Longer detail description | `description.vi` / `description.en` |
| Search synonyms | `aliases`, e.g. `["white coffee", "bạc sỉu"]` |
| Price | The appropriate `variants` entry's `price`, as integer VND: `55000`, not `55` or `"55.000đ"` |
| Size/temperature wording | Variant `label` in both languages; update `attributes` as appropriate |
| Preparation time | Optional `preparationMinutes`, e.g. `15`; remove it if no preparation note is needed |
| Best seller | `badges: ["bestseller"]` |
| Must try | `badges: ["must-try"]` |
| No badge | `badges: []` |
| Photo | Photo mapping + image script, not the generated asset JSON |

Catalog and search rows show **the first variant's price**. It is not automatically the minimum. Put the desired starting variant first; all variants and prices are shown in details. Changing this first price may move a drink in its category because drinks sort by price descending. Equal-priced drinks retain their order in `products`. Food and toppings retain their order in `products`.

If you list both badges, the catalog displays the first and details display both. For renamed dishes with photos, regenerate that dish's photos to refresh generated photo alternative text.

Only `S` and `M` are supported in `attributes.size`, and only `hot` / `cold` in `attributes.temperature`. A new structured size such as `L` requires updating the schema in `src/domain/menu.ts`; a label alone is free text. `sourceCodes` preserves PDF import markings and is not a customer-facing badge or an automatic offer rule. Use `[]` for new items unless you have a source code to retain.

### Temporarily unavailable versus removed

Set a dish's `availability` to `"unavailable"` when it is temporarily sold out. It stays visible in the catalog and search, with an unavailable label. Restore `"available"` when it returns.

For only one sold-out size, change that variant's availability. A dish remains available if the dish and at least one variant are available. The first-variant catalog price still applies even if that particular variant is unavailable. There is currently no separate “hide this dish” setting.

### Options, substitutions and free toppings

Options are displayed for reference; this site does not take an order or calculate a configured drink total.

- `optionGroups` defines the choices and their `priceDelta` (extra charge in integer VND; `0` means free).
- `optionGroups[].variantIds` restricts a group to listed variant IDs. Keep these IDs aligned with the dish's variants.
- `variants[].benefits` adds the inclusion/offer text next to the applicable price and references the group through `groupId` and its choices through `choiceIds`.
- Do not copy a free benefit into every size by accident. In the current menu, the marked free-topping offers apply only to the M variant.
- All seven current toppings qualify for those offers. The choices are copied into each eligible drink's `free-toppings` group; they are **not automatically linked** to topping products. Adding/removing/renaming a topping requires updating every affected group's choices and benefit `choiceIds`. Paid add-ons are also separate records.
- Existing examples to copy carefully: `tra-buoi` for an M-size free-topping offer; `matcha-latte` for the free oat-milk substitution; `cup-noodles` for charged extras. Search those product IDs in `products.json`.
- Leave unspecified `maxSelections`, `maxQuantity`, and benefit `quantity` absent unless you have confirmed rules. Do not guess quantities.

For a simple dish without options, retain `optionGroups: []` and `benefits: []`.

## Remove a dish permanently

1. If its ID appears in `discovery.featuredProductIds`, replace or remove that reference in `src/data/menu.ts`.
2. Remove its object from `products.json`.
3. If it has a photo mapping, remove its entire key from `scripts/product-photos.json`.
4. Remove generated photo references and unused generated files, replacing `bac-xiu` with the deleted ID:

   ```sh
   npm run photos:prepare -- --remove bac-xiu
   ```

   This does not need the source folder and does not delete originals. It also works if the product has already been removed. Unrelated photos are retained.

5. If this is a topping or add-on, update any copied option choices and associated benefit references as described above.
6. Run the two validation commands and review the preview. Photo-reference errors between steps 2–4 are expected until cleanup is complete.

## Final review and troubleshooting

Check the changed category, dish, details, search results, both languages, and a narrow phone-sized viewport. For photo changes, also check the first image and any extra views.

| Message/symptom | Fix |
| --- | --- |
| JSON syntax error | Check missing/extra commas, double quotes and closing brackets |
| Duplicate ID | Give a new record a new ID; do not duplicate an existing one |
| Unknown category | Correct the dish's `categoryId`, or create that category |
| Unknown Discovery product/target | Update Discovery after deleting or renaming an ID |
| Unknown photo product / stale mapping | Remove the mapping and run the `--remove` command |
| Missing menu image | Regenerate the mapped dish or restore generated assets and manifest together |
| Changed a source photo but website still shows old photo | Run `photos:prepare --only ID`; saving the source alone does not regenerate it |
| New drink category isn't price-sorted | Add its ID to `drinkCategories` as described above |

`npm test` and `npm run test:e2e` include regression checks against the original PDF import (counts, specific prices, IDs and offers). Intentional menu changes may require updating those test expectations; do not undo a valid menu edit just to preserve the old snapshot. Use `menu:check` and `build` for routine content validation, then update the affected regression checks when maintaining the code/tests. Do not disable unrelated tests.
